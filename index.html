Short case studies from my security work: the problem, the approach, and what I took away.

01

Building and hardening a human-approved automation agent

Threat Modeling Cloudflare Workers Microsoft Graph
Problem

A two-person security team was handling privileged, repetitive requests by hand: MFA resets, distribution-list changes and offboarding across two Microsoft 365 tenants. Manual work was slow, and any request arriving by chat or ticket can be spoofed by someone impersonating an employee.

Approach

I built “Shifty” as a Cloudflare Worker that talks to Microsoft Graph, Freshservice and Slack. Every privileged action is proposed, approved by a human in Slack, logged, and version-controlled in GitHub. The same pattern powers an /offboard flow (session revocation, sign-in block, group-owner reassignment, OneDrive archival, Slack and Zoom deactivation) and has been replicated for a second business unit.

Threat model

I designed against four failure modes: impersonated requests, over-privileged automation credentials, privileged actions with no audit trail, and unreviewed changes to the agent itself. The controls map one to one: human approval, scoped permissions, logging, and pull-request history.

What I learned

Automation should reduce the work, not the oversight. A human approval step costs seconds and removes the whole class of failures where the bot did something nobody authorized.

04

Migrating 288+ distribution lists safely

PowerShell Exchange Online Change Safety
Problem

Hundreds of legacy distribution lists across two Exchange Online tenants had orphaned owners, nested membership and unnecessary licensing cost, with no safe way to change them at scale.

Approach

I wrote a PowerShell migration to Microsoft 365 Groups with -WhatIf simulation, orphaned-owner reassignment, SMTP and GAL preservation, nested-membership flattening and full rollback. It contributed to $61K+ in annual licensing savings. A follow-up guarded cleanup script processed 394 lists and flagged 260 stale memberships.

What I learned

Make the dangerous script prove itself first. Simulation mode and a tested rollback turned a tenant-wide change into something safe to run with confidence.

Secure by design

How I secured Peach & Pit.

Journal entries are personal, so security shaped the app from the start. The guiding assumption: anything inside a mobile app can be extracted, so the client is never trusted.

Authentication

Firebase Authentication

Sign-in runs through Firebase Authentication, so credential storage, hashing and session tokens are handled by a mature identity service instead of code I wrote myself.

Authorization

Firestore Security Rules

Access is enforced server-side with Firestore Security Rules. A user can only read and write the data the rules allow, no matter what the app sends.

User data

Close-circle model

Entries are shared with people the user chooses, not published publicly. I collect only what the product needs to work.

Secrets

Server-side by default

No private keys or service credentials ship inside the app. Privileged logic stays server-side, and secrets are kept out of the repository.
